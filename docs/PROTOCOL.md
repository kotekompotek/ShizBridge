# ShizBridge Protocol v1

Transport: **every** connection to the phone's single TCP port (default
**8787**) starts with a TLS handshake (TLS 1.3 preferred, 1.2 fallback).
TLS 1.3 post-handshake client auth is used, so both pairing and data
sessions authenticate the client certificate at the TLS layer.

After the handshake the client sends a short ASCII **magic** that selects
the session type (first 4 bytes):

| First bytes | Mode |
|---|---|
| `SBPR` | **Pairing handshake** (framed JSON, then encrypted) |
| `SBCT` (+`L`, total `SBCTL`) | **Control channel** (framed JSON) |
| anything else | **Relay** — raw ADB bytes, transparently piped to adbd |

> Design note: TLS-first removes the need to peek the plaintext stream on
> Android (JSSE cannot push back a consumed byte into an `SSLSocket`).
> Pairing is additionally protected end-to-end by its own ECDH + code
> proof, so an unauthenticated TLS layer during pairing leaks nothing:
> a MITM can only relay, never read or forge.

## 1. Frame codec (pairing + control)

Framed messages (pairing after `SBPR`, control after `SBCTL`):

```
+----------------+---------------------------+
| u32 BE length  | UTF-8 JSON payload        |
+----------------+---------------------------+
```

Maximum frame size: 65536 bytes. Oversized frames → close connection.

## 2. Pairing handshake (v1)

Goal: establish an encrypted channel bound to a one-time pairing code,
exchange self-signed identity certificates, pin the server certificate
on the client and enroll the client certificate on the server.

Start: client connects (TLS, pin not yet known → client does not verify
the chain; server already requires a client certificate) and writes the
4-byte magic `SBPR`.

Goal: establish an encrypted channel bound to a one-time pairing code,
exchange self-signed identity certificates, pin the server certificate
on the client and enroll the client certificate on the server.

Code: 12 chars Crockford base32 (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`),
generated by the phone, TTL 300 s, max **3 attempts** per code
(then 10-minute server-side lockout).

### Keys

* ECDH: **NIST P-256** (`secp256r1`), ephemeral per handshake.
* KDF: **HKDF-SHA256** (RFC 5869).
* Channel encryption: **AES-256-GCM**, 12-byte nonce (below).
* Identity: self-signed **ECDSA P-256 / SHA-256** X.509 certificates (DER),
  referenced by `SPKI-SHA256` (Base64 of SHA-256 over SubjectPublicKeyInfo).

### Derivation

```
shared    = ECDH(eph_priv, peer_eph_pub)
salt      = client_nonce || server_nonce          (16 + 16 bytes)
key       = HKDF-SHA256(ikm = shared, salt = salt,
                        info = "ShizBridge pairing v1", L = 32)
```

### Frame encryption (from message #3 on)

Each JSON payload after `pair_hello` exchange is encrypted:

```
frame     = AES-256-GCM.encrypt(key, nonce, aad = "", plaintext = JSON)
nonce     = dir || counter_be_u64 || 0x00 0x00 0x00
            dir = 0x01 (client→server) | 0x02 (server→client)
            counter starts at 0, +1 per frame, per direction
```

Encrypted payload is sent in the same length-prefixed framing
(length = len(ciphertext||tag)).

### Message sequence

```
C → S   {"t":"pair_hello","v":1,"eph_pub":"<b64 raw P-256 uncompressed>","nonce":"<b64 16>"}
S → C   {"t":"pair_hello","v":1,"eph_pub":"...","nonce":"...","srv_cert":"<b64 DER>"}
        (both derive `key`; from now on frames are AES-GCM encrypted)

C → S   {"t":"pair_auth","proof":"<b64 HMAC-SHA256(key, \"ShizBridge code proof\" || code)>",
         "cli_cert":"<b64 DER>","label":"<client name>"}
S → C   {"t":"pair_result","ok":true,"fp":"<SPKI-SHA256 of srv_cert, Crockford-free hex, lowercase, no separators>"}
   or   {"t":"pair_result","ok":false,"reason":"bad_code"|"locked"|"expired"}
```

On `ok:true`:

* **Server** stores `SPKI-SHA256(cli_cert)` in the allowlist (persistent) and
  associates the client `label`.
* **Client** stores `fp` as the pinned server fingerprint in its config.
* Code is invalidated (single-use).

Notes:

* The proof binds the code to the ephemeral ECDH key agreement; a passive
  observer without the code cannot complete the handshake, an active MITM
  without the code fails at `pair_auth`, and a passive observer *with*
  captured traffic cannot recover the code (HMAC with 256-bit key).
* Constant-time comparison of `proof` on the server.

## 3. Data session (post-pairing)

1. Client dials TCP, sends TLS **ClientHello** (TLS 1.3 preferred),
   presenting its identity certificate.
2. Server: `ClientAuth = RequireAnyClientCert`; verifies client cert
   SPKI is in the allowlist (no CA chain validation — pin-based trust).
   Connections with magic `SBPR` are exempt (that is the pairing flow,
   authenticated by the code proof instead).
3. Client: verifies the server cert's SPKI-SHA256 equals the pin
   captured at pairing (during pairing itself: no pin yet, see above).
4. After the handshake the channel is a **transparent byte pipe**:

   * **Relay mode** (default): both directions are copied verbatim between
     the TLS socket and `127.0.0.1:<adbd_port>` on the phone. The first
     4 bytes that are neither `SBPR` nor `SBCT` are pushed back and flow
     to adbd untouched (ADB CNXN/AUTH/OPEN/WRTE…, sync, scrcpy).
   * **Control mode**: if the first 5 bytes received from the client are
     ASCII `SBCTL`, the connection is a JSON control channel instead
     (never mixed with relay on one connection).

### Control channel

After `SBCTL` the stream is again length-prefixed JSON frames (same codec).

```
C → S   {"op":"ping"}
S → C   {"op":"pong","ts":<unix ms>}

C → S   {"op":"info"}
S → C   {"op":"info","app":"ShizBridge","proto":1,"ver":"0.1.0",
         "adbd_port":5555,"adbd_up":true,"clients":1,
         "shizuku":"running|stopped|unsupported"}
```

## 4. ADB port on the phone

MVP: auto-detect by parsing `/proc/self/net/tcp{,6}` for loopback
LISTEN sockets and probing candidates with a real ADB `CNXN` exchange;
manual override in the app UI.
Phase 2: Shizuku-based discovery (`mdns services` / wireless-debugging
state) and `adb tcpip` control.

## 6. Threat model (summary)

| Adversary | Prevented by |
|---|---|
| Passive network eavesdropper | TLS 1.3 + WireGuard/Tailscale underneath |
| Active MITM during pairing | ECDH + code proof (end-to-end, independent of TLS) |
| Brute force of pairing code | 60-bit code, 3 attempts, 10-min lockout, TTL |
| Random device on the tailnet | mTLS: client cert must be in allowlist |
| Malicious app on the phone | Server requires client cert; allowlist revocable in UI |
| Stolen/lost PC | Revoke client in app → next connection rejected |
